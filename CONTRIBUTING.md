# Contributing a Shard

Read [what a Shard can and cannot do](docs/what-a-plugin-can-do.md) and the [guide](docs/writing-a-plugin.md) first.

## What a pull request contains

- the source in `plugins/<id>/` (`manifest.json`, the entry file, a short `README.md`); start from `node scripts/new.cjs <id>`;
- `dist/<id>-<version>.vplugin` and `index.json`, generated by `node scripts/build.cjs`. CI runs
  `node scripts/build.cjs --check` and fails when a Shard breaks a rule below that a machine can check, or when they
  are out of date;
- a new `version` for every change to an existing Shard. The hash in `index.json` must always describe a
  published version, so a changed bundle with the same version is refused (CI compares with `main`).

Do not add a signature yourself. The post-merge publisher signs reviewed entries
into the separate `catalog` branch; `main/index.json` remains a build input.

Run `npm ci --ignore-scripts`, `npm test`, `npm run check` and
`npm run test:runtime` before submitting. CI repeats the lifecycle checks on
Node 4.4.7, 12.4.0 and 20; use only ES5 in Shard files. `start()`/`stop()` must release
timers and sockets across restarts. Fake TV command responses in smoke tests are
not proof of working on real hardware: include your model and actual test results. For a card, say what you saw on the
Control center itself (Vetro 0.7.0 or later), or say that you did not try it on a TV.

The required `check` must pass and a code owner must approve an ordinary merge.
Administrators retain their existing explicit bypass; the publishing key must
never be supplied to PR jobs, a Shard test, or a `pull_request_target` workflow.

## What the maintainer checks

- The code is readable: no minified or obfuscated source, no `eval` or `new Function`, no downloaded code (the one exception is a large helper, see below).
- It talks only to what the description says. No network calls to hosts the description does not mention, no
  collection of data about the user, the TV or the network.
- `permissions` is as small as possible. A Shard that asks for `exec` must say in its README which commands it
  runs and why; a Shard that does not need `exec` must not ask for it.
- It cleans up in `stop()` (timers, sockets) and keeps its own data in its folder or in `ctx.config`.
- **A Control center card** (`controlCenter` in the manifest, [guide](docs/writing-a-plugin.md#adding-a-card-to-the-control-center)):
  the README says what the rows show and what OK on a row does. `card()` only reads and answers inside 3 seconds; `cardSelect(rowId)` acts
  only on rows that `card()` lists, answers inside 10, and never turns something on or off that the user did not put on the card. A key
  press on a remote must not open a door or disarm an alarm. Neither method throws on a missing config or an unreachable service: it
  resolves or rejects with a short message the user can read (`Token refused`). `npm run test:runtime` calls both with an empty config.
- The `author` is a real GitHub account that can answer questions about the Shard.

## A helper too big for the bundle

A bundle is at most 512 KB and text only. A small helper goes inside it as text (`eightbitdo-guide`: a `.gz.b64` file
whose SHA-256 CI checks). A compiled helper too big for that, such as the `nordtv` Go program of `vpn`, may instead
live in `helpers/` of this repository and be downloaded by the TV from
`https://raw.githubusercontent.com/andrearicci93/vetro-plugins/main/helpers/`, and only from there. It is the only
code a Shard may download, and only if all of this holds:

- the source is in the pull request, and CI rebuilds the helper from it byte for byte with a pinned toolchain
  (`scripts/check-helpers.sh`, job `helpers`). The check must fail when the file in `helpers/` is not what the source builds to;
- the Shard pins the SHA-256 of the downloaded file in its code, checks it before it runs or unpacks anything, and
  refuses to run it on a mismatch. Never a version "latest", never another host or a release of the author;
- the README states both hashes (the file and the program inside it) and what the helper does as root;
- the file has a new name for every change (`nordtv-1.1.2.gz`), so a Shard version always points to the file it was reviewed with.

The helper gets the same review as the rest of the code: no obfuscation, no host the description does not mention, no
data collected.

This is a spot check by one person, not an audit.

## Removal

Remove the source folder from `plugins/` and rebuild `index.json` and `dist/` when a Shard is reported as unsafe,
stops working on current firmware or Vetro, or its author asks. Merge the removal so the publisher removes the
entry from the signed `catalog` branch too. Removal does not uninstall it from TVs that already
have it: tell users to switch it off and remove it from the dashboard.
